# TripMate — ассистент путешественника

Учебный проект, домашнее задание №1: локальные модели, OpenRouter, консольный чат
и агент, который вызывает функции, **разбирая их прямо из текста ответа** — без `function calling`,
`tools` API и MCP.

Домашнее задание №2 — чат-агент на LangChain с памятью фактов в файле — в [разделе ниже](#дз-2-langchain-агент-с-памятью-фактов) и в папке [`hw2/`](hw2/).

## Предметная область

**TripMate** помогает спланировать поездку. Пользователь спрашивает обычным языком, а ассистент
сам решает, какие данные нужны, и вызывает инструменты (данные — захардкоженные константы):

| инструмент | что делает |
|---|---|
| `get_weather(city)` | текущая погода в городе |
| `get_local_time(city)` | местное время и дата (реальное время по таблице часовых поясов) |
| `convert_currency(amount, from_currency, to_currency)` | конвертация по фиксированным курсам |
| `get_attractions(city)` | главные достопримечательности |
| `search_flights(origin, destination)` | авиабилеты с ценами в рублях |

Города: Москва, Санкт-Петербург, Париж, Рим, Стамбул, Токио, Дубай, Барселона (принимаются и
русские, и английские названия). По другим городам инструмент честно возвращает `error`.

## Структура

```
chat.py               # задание 3 — REPL-чат со стримингом
assistant.py          # задание 4 — TripMate с инструментами
evaluate.py           # задания 4.1/4.2 — прогон сценариев, логи в logs/
tripmate/
  config.py           # модели: qwen, llama (локально), openrouter
  llm.py              # стриминг через OpenAI-совместимый API (без параметра tools)
  tools.py            # инструменты и данные
  parser.py           # разбор <tool_call>{...}</tool_call> из текста
  prompts.py          # промпты v1…v5 (итерации prompt engineering)
  agent.py            # цикл «ответ → вызов → результат → ответ»
scripts/start_local.sh, stop_local.sh
logs/                 # <модель>__<промпт>.log + summary.md
```

## Запуск

```bash
brew install llama.cpp
# модели (~2 ГБ каждая) кладутся в models/
curl -L -o models/qwen2.5-3b-instruct-q4_k_m.gguf https://huggingface.co/bartowski/Qwen2.5-3B-Instruct-GGUF/resolve/main/Qwen2.5-3B-Instruct-Q4_K_M.gguf
curl -L -o models/llama-3.2-3b-instruct-q4_k_m.gguf https://huggingface.co/bartowski/Llama-3.2-3B-Instruct-GGUF/resolve/main/Llama-3.2-3B-Instruct-Q4_K_M.gguf

scripts/start_local.sh                 # qwen -> :8081, llama -> :8082 (+ qwen -> :8083 для ДЗ 2)
cp .env.example .env                   # вписать OPENROUTER_API_KEY для облачной модели

uv run chat.py --model llama           # 3. простой чат
uv run assistant.py --model qwen       # 4. ассистент (промпт v5 по умолчанию)
uv run evaluate.py                     # 4.1/4.2. qwen+llama × v1…v5 -> logs/
uv run evaluate.py --models openrouter --prompts v1 v5   # эталон из облака
```

В чатах: `/reset` очищает историю, `/exit` или Ctrl+D — выход, Ctrl+C прерывает генерацию.

> **Важно:** в llama.cpp 0.7 jinja-шаблоны включены по умолчанию, и сервер сам вырезает
> `<tool_call>…</tool_call>` из ответа (встроенный парсер tool calls для Qwen/Hermes).
> Поэтому серверы запускаются с `--skip-chat-parsing`: модель отдаёт сырой текст,
> а вызовы разбирает наш `parser.py`.

## Как устроен вызов функций

1. В системном промпте описан формат: `<tool_call>{"name": ..., "arguments": {...}}</tool_call>`.
2. Генерация останавливается stop-последовательностью `</tool_call>`, поэтому модель не успевает
   «придумать» результат за систему.
3. `parser.py` терпим к ошибкам слабых моделей: незакрытый тег, ```json-обёртка, одинарные
   кавычки, `parameters` вместо `arguments`, аргументы на верхнем уровне, JSON без тегов.
4. Результат возвращается сообщением `<tool_result name="...">{json}</tool_result>`; ошибки
   (неизвестный город, нет аргумента, битый JSON) тоже уходят модели, чтобы она могла исправиться.

## Результаты (4.1 и 4.2)

10 сценариев, temperature=0. Проверки: нужные инструменты вызваны (или ни одного, если не нужны),
формат без ошибок, ответ содержит факты из инструментов, нет признаков выдуманных данных.
Полные трассы лежат в `logs/<модель>__<промпт>.log`, таблица — в [`logs/summary.md`](logs/summary.md).

| промпт | qwen2.5-3b | llama-3.2-3b | что поменяли |
|---|---|---|---|
| v1 | 3/10 | 3/10 | наивный: роль + список функций + формат |
| v2 | 8/10 | 8/10 | запрет выдумывать данные, строгие правила формата, few-shot диалоги |
| v3 | 8/10 | 6/10 | примеры перенесены в системный промпт, правило «покрой все части вопроса», исходный вопрос повторяется после каждого результата |
| v4 | 8/10 | 8/10 | few-shot снова настоящими сообщениями + разделитель «конец примеров», пример «совет без инструментов», «не подменяй город» |
| **v5** | **10/10** | **9/10** | plan-and-execute: модель пишет `План: tool1, tool2`, агент подсказывает, что осталось, и один раз останавливает преждевременный ответ; сравнение чисел со знаком `>`/`<` |

Что видно по логам:

- **v1.** Qwen с наивным промптом почти всегда сразу выдаёт `<|im_end|>`: вероятность пустого
  ответа 0.61 против 0.27 у `<tool_call>`. Llama вместо вызова сама начинает писать фейковый
  `<tool_result>` с выдуманной погодой. Его отрезает stop-последовательность, поэтому в логе
  ответ пустой.
- **v2.** Строгие правила и few-shot дают основной прирост. Но few-shot «протекал»: на вопрос про
  Стамбул Qwen ответил ценой билета в Петербург из примера и не вызвал ни одного инструмента.
- **v3.** Текстовые примеры Llama копирует слишком буквально: вызывает 5 инструментов на вопрос
  «как собрать чемодан» и, не найдя Урюпинск, подставляет Москву.
- **v4.** Протечка и подмена города ушли. Остались составные вопросы: Qwen после погоды
  «досочиняет» достопримечательности Рима (Палаццо Веккьо, который во Флоренции).
- **v5.** План в первой строке и подсказка «осталось: get_attractions» закрыли составные вопросы
  у обеих моделей. Последняя ошибка Llama — арифметика: пишет «27750 ₽ < 21400 ₽, значит не
  хватит». У 3B-моделей это обычное слабое место; надёжнее было бы отдать сравнение отдельному
  инструменту.

## ДЗ 2. LangChain-агент с памятью фактов

TripMate проводит короткую анкету путешественника: имя, город вылета, направление, даты,
бюджет, с кем едет, интересы, плюс свободные факты вроде «аллергия на орехи». Факты сохраняются
в `hw2/memory.json`. После перезапуска агент здоровается по имени, не переспрашивает известное
и продолжает с первого незаполненного вопроса.

```
hw2/memory_agent.ipynb   # ноутбук: весь код + демонстрация (уже выполнен)
hw2/memory.json          # файл памяти после демонстрации (профили alex и maria)
hw2/run_demo.py          # выполняет ноутбук двумя сессиями в двух разных процессах ядра
```

```bash
scripts/start_local.sh   # нужен сервер :8083
uv run hw2/run_demo.py   # перевыполнить ноутбук: сессия 1 → новый процесс → сессия 2
```

Вручную: открыть ноутбук, выполнить раздел 1 (код) и раздел 2, затем *Kernel → Restart*, снова
раздел 1 и раздел 3. Для живого диалога — `INTERACTIVE = True` в последней ячейке.

**Как устроено**

| требование | реализация |
|---|---|
| чат на LangChain | `ChatPromptTemplate \| ChatOpenAI \| StrOutputParser` в `RunnableWithMessageHistory` |
| память — факты, не история | `FactMemory(BaseChatMemory)`: `load_memory_variables()` отдаёт факты и следующий вопрос, `save_context()` извлекает факты и пишет файл; история сообщений живёт только в рамках запуска |
| извлечение фактов | отдельный LLM-вызов, `with_structured_output(..., method="json_schema")` |
| файл при старте | есть — читаем, нет — пустая память; запись атомарная |
| несколько профилей | `user_id` = `session_id`, все профили в одном `memory.json` |
| служебный вывод в отдельной CELL | `ServicePanel`: ячейка создаётся один раз и обновляется на месте через `display_id` |

**Что пришлось решить для 3B-модели** (все случаи видны в служебной панели ноутбука):

- `--skip-chat-parsing` из ДЗ 1 отключает JSON-грамматику для `response_format`, поэтому для ДЗ 2
  поднят отдельный сервер на :8083 без этого флага.
- Получив сразу все 7 полей, Qwen 3B путал их: «аллергия на орехи» уходила в интересы, а из
  встречного вопроса «а в ноябре там не холодно?» получались выдуманные даты. Поэтому во время
  анкеты извлекается только ответ на заданный вопрос (`SlotAnswer` с флагом `answered`). Из той же
  реплики дополнительно берутся имя, город и направление («я Мария из Новосибирска» — город потом
  не спрашивается). Полная схема работает после анкеты, когда меняются любые факты («летим в Рим»).
- Проверка обоснованности: факт принимается, только если его слова есть в реплике пользователя.
  Так отсекаются, например, «Бюджет = bytes» и варианты, скопированные из текста вопроса.
- Следующий вопрос анкеты выбирает код, а не модель. Модель только коротко реагирует на реплику;
  её собственные вопросы во время анкеты вырезаются. Иначе 3B-модель задаёт два вопроса сразу.

Ограничение: память работает надёжно, но свободные ответы 3B-модели иногда содержат неточности
(например, выдуманные названия улиц в Риме). Это качество самой генерации, а не памяти.
